# Ведение проекта и память

Связующее звено между dev-spec → dev-build → dev-test: **отслеживать этапы, помнить
решения и продолжать с того же места.** Без этого каждая сессия начинается с нуля —
агент переспрашивает, переделывает, забывает, почему выбрали этот стек.

## Когда активирован

- «Начнём проект» / «создай проект» — заводит папку и журнал.
- Возврат к работе: «продолжим», «на чём мы остановились», «что дальше».
- «Сохрани прогресс», «запиши решение», «покажи статус проекта».
- В начале любой новой сессии по существующему проекту — **протокол возобновления**.

**Не активируй** для написания кода (dev-build), тестов (dev-test) или ТЗ (dev-spec) —
эти навыки сами делают свою часть; этот навык её фиксирует.

## Два уровня памяти

1. **Память агента (глобальная, кросс-проектная)** — `~/.agenthere/memory/ai-developer/`
   — в домашней директории пользователя (Windows — `%USERPROFILE%\.agenthere\memory\ai-developer\`),
   не в рабочей директории:
   - `stack.md` — предпочтения пользователя: ОС, установленные рантаймы (Node/Python),
     любимый стек, кодировки/пакетный менеджер. Один раз узнал — больше не переспрашиваешь.
   - `decisions.md` — кросс-проектные паттерны и принципы, которые пользователь хочет
     соблюдать всегда.
   - `projects.md` — индекс проектов: название, путь к папке, статус, дата.
2. **Журнал проекта (per-проектный)** — в папке самого проекта:
   - `SPEC.md` — ТЗ (ведёт dev-spec).
   - `DEV-JOURNAL.md` — статус, решения, что дальше, чек-лист. Шаблон — в конце
     этого навыка.

Глобальная память — про **пользователя**; журнал проекта — про **конкретную работу**.

## Протокол возобновления (КАЖДУЮ новую сессию по проекту)

В самом начале разговора, если есть существующий проект:

1. Прочитай `~/.agenthere/memory/ai-developer/` (все файлы) — узнаешь пользователя.
2. Найди папку проекта (спроси путь, если неоднозначно) и прочитай `DEV-JOURNAL.md` +
   `SPEC.md`.
3. Кратко перескажи пользователю: **на чём остановились, что decided, что делаем сейчас**.
4. Продолжай с первой невыполненной задачи в чек-листе журнала.

Это превращает «начать заново» в «продолжить». Без журнала агент честно скажет: «Не
вижу журнала проекта — давай создадим или уточни путь».

## Заведение нового проекта

1. Создай папку проекта (или используй текущую рабочую).
2. Положи туда `SPEC.md` (через dev-spec) и `DEV-JOURNAL.md` (из шаблона).
3. Запиши проект в `~/.agenthere/memory/ai-developer/projects.md`.
4. Узнай окружение один раз и сохрани в `stack.md`: ОС, есть ли Node/Python, пакетный
   менеджер, любимый язык. **Больше не переспрашивай.**

## Журнал — что и когда записывать

Журнал (`DEV-JOURNAL.md`) ведёт навык dev-project, но **записывают все этапы**:

| Событие | Что записать | Когда |
|---|---|---|
| Решение по архитектуре/стеку | что выбрали + **почему** + отвергнутые альтернативы | сразу в dev-spec |
| Готовая задача из чек-листа | `[x]` + дата | сразу в dev-build после коммита |
| Найденный/починенный баг | кейс + корень + фикс | сразу в dev-test |
| Деплой | URL, хостинг, как обновлять, где env | сразу в dev-deploy |
| Новая задача всплыла | `[-]` строка в чек-лист | когда обнаружили |
| Решение «не делать в MVP» | что и почему отложено | сразу |

**Правило немедленной фиксации:** узнал/решил/закончил → **сразу** запиши. Не откладывай
на конец сессии — к концу забудется половина, а контекст мог сжаться.

## Чек-лист задач (todowrite)

Для активной работы используй инструмент `todowrite` — живой чек-лист текущей сессии
(быстро, в контексте). Журнал `DEV-JOURNAL.md` — **долговечная** запись между сессиями.
Связь: завершённую задачу из todowrite отметь и в журнале (`[x]` + дата).

## Что НЕ хранить

- Болтовню, временные состояния, логи разговоров, дубликаты.
- То, что легко перепроверить (содержимое файлов — есть же `read`).
- **Секреты, токены, пароли, ключи API — никогда.** (РФ-резидентность данных: память
  живёт на машине пользователя; пихать туда секреты — риск.)
- Журнал — до ~150 строк; если разросся — архивируй старое в `DEV-JOURNAL.archive.md`.

## Границы (✅ / ⚠️ / 🚫)

- ✅ **Всегда:** протокол возобновления в начале сессии; запись решения сразу; обновлять
  чек-лист после каждого среза.
- ⚠️ **Спросить:** перед удалением/архивацией больших кусков журнала; перед сменой
  зафиксированного решения (объясни, что меняется и почему).
- 🚫 **Никогда:** не хранить секреты; не перезаписывать чужие файлы журнала без
  подтверждения; не врать в статусе («готово», когда не запускалось).

## Выходные критерии

- [ ] В начале сессии по существующему проекту выполнен **протокол возобновления**.
- [ ] Каждое решение/завершённая задача/баг **записаны** в журнал.
- [ ] `stack.md` хранит окружение пользователя (чтобы не переспрашивать).
- [ ] Чек-лист в журнале отражает реальное состояние (что сделано, что дальше).
- [ ] Нет секретов в памяти/журнале.

## Шаблон DEV-JOURNAL.md

Кладётся в корень проекта рядом с `SPEC.md`. Живой документ — обновляй по ходу;
архивируй старое в `DEV-JOURNAL.archive.md`, когда активная часть перевалит за ~150
строк. Чек-лист отражает **реальность**: `[x]` только для запущенного и проверенного.

```markdown
# DEV-JOURNAL — <название проекта>

**Статус:** <идея / в разработке / готов MVP / на паузе>
**Начат:** <дата> · **Обновлён:** <дата>
**Стек:** <из SPEC.md, одна строка>
**Цель (из SPEC):** <одна фраза>
**Деплой:** <URL / ещё не деплоили>

## Что сделали (кратко)
- <дата> — <что> (commit/файл).
- <дата> — <что>.

## Текущий этап
<одна-две строки: над чем работаем прямо сейчас>

## Чек-лист задач
- [x] <задача> — <дата>
- [ ] <задача> ← текущая
- [ ] <задача>
- [-] <отложено из MVP: что и почему>

## Журнал решений
- <дата> — **Решили:** <X> вместо <Y>. **Почему:** <причина>. **Альтернативы:** <что
  отвергли>. *(Защищает от «а почему так?» через месяц и от отката к худшему.)*

## Баги и фиксы
- <дата> — **Баг:** <симптом>. **Кейс:** <как воспроизвести>. **Корень:** <почему>.
  **Фикс:** <что сделал>. **Тест:** <имя теста, который закрыл кейс>.

## Что дальше (next)
1. <следующая задача>
2. <задача>

## Заметки
<подводные камни, зависимости, что узнать у пользователя>
```

## Правила ведения журнала
- Записывай **сразу** после события (решение / коммит / фикс) — не откладывай на конец.
- Решение без причины бесполезно — всегда пиши **«почему»**.
- Завершённые этапы архивируй, когда активная часть перевалит за ~150 строк.
